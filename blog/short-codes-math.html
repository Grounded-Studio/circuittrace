Engineering

The math behind short codes.

📅 17 October 2026 · ⏱ 8 min read · ✍️ Grounded Studio

When you tap SHARE in the Circuit Trace editor, you get back something like this:

CT-NHH06-8CMY4-AG2DS-7FQ3B

Twenty characters. Enough to encode a full 8×8 puzzle with 7 colour pairs, 4 diodes, and a seed for the solver cache. Here's how we got there — and why we didn't just stuff a URL into the share sheet.

The problem with URLs

The obvious first instinct is to share a link: circuittrace.app/puzzle?data=.... That works, but it has three annoying failure modes:

  • WhatsApp strips URL parameters. Not always, but often enough. If a preview-scraper rewrites your link, your puzzle data goes with it.
  • No app, no puzzle. If your friend doesn't have Circuit Trace installed, a URL opens a browser instead of the game. They need to install, come back, re-click.
  • URLs look ugly. A 60-character blob with equals signs and percent-encoding isn't something you WhatsApp to your mum.

We wanted a code you could say out loud over the phone if you had to. A code someone could type by hand from a screenshot. A code that would survive copy-paste through five different apps.

Step 1: what's in a puzzle

A Circuit Trace puzzle is a surprisingly small amount of data:

  • Grid size (5-8) → 2 bits
  • Up to 7 colour pairs, each with two cell positions → 7 × 2 × 6 = 84 bits (6 bits is enough to address 64 cells on an 8×8)
  • Up to 6 diodes, each with position + direction → 6 × 8 = 48 bits
  • Version number so we can evolve the format → 3 bits
  • A tiny checksum so we can detect typos before we try to parse → 8 bits

Total: about 145 bits worst-case. In practice most puzzles use less, because most puzzles have 4-5 pairs and 0-2 diodes.

Step 2: Crockford Base32

145 bits ÷ 5 bits per character = 29 characters in standard Base32. Too long for a WhatsApp message. We needed to pack smarter and encode more efficiently — but the alphabet matters too.

Standard Base64 uses A-Z a-z 0-9 + /. Terrible for sharing by voice ("capital B? or lowercase?"), terrible for OCR ("is that a lowercase L or a 1?"), and the + and / characters break in URLs anyway.

We use Crockford Base32 instead. Douglas Crockford's variant is 32 characters chosen specifically to be unambiguous when humans copy them:

  • Uses all uppercase only — no capitalisation confusion
  • Drops I, L, O, and U entirely — removes every character that looks like a digit
  • Decoder accepts i and l as 1, and o as 0 — forgiving if someone mistypes
  • Also accepts lowercase in the decoder — forgiving if someone shout-types or auto-corrects

Net effect: the alphabet is still 32 characters wide (5 bits per char), but a human can read a code over the phone and the person on the other end types it correctly on the first try.

Step 3: variable-length packing

Fixed-width fields waste bits. A 5×5 grid only needs 5 bits per cell address, not 6. A puzzle with 3 pairs doesn't need to reserve space for 7.

So we pack length-prefixed: 2 bits for grid size, 3 bits for pair count, then that many pair records, each sized for the grid. Same for diodes. The decoder walks the bitstream in order and knows exactly how much to read.

Average puzzle: 85-110 bits. Rounded up to a multiple of 5 bits, that's 17-22 Base32 characters. We then insert dashes every 5 characters for readability — turning NHH068CMY4AG2DS7FQ3B into NHH06-8CMY4-AG2DS-7FQ3B. Dashes are stripped during decode, they're purely for human eyes.

Step 4: the CT- prefix

Every code starts with CT-. Not just branding — it's the format marker. If someone copies a Base32 string from somewhere else, the editor can tell immediately it's not a Circuit Trace code and show a helpful error ("that doesn't look like a Circuit Trace puzzle") instead of garbling a decode attempt.

The prefix also lets us scan for codes in the clipboard: when you open the editor's "PLAY SHARED CODE" screen, we peek at the clipboard, and if it starts with CT-, we offer to paste it automatically. One less tap.

Step 5: the checksum

The last byte of every encoded puzzle is a checksum of everything before it. Tiny — just 8 bits — but enough to catch 99.6% of single-character typos. If the checksum fails, the decoder bails before it tries to render anything, and the player sees "This code looks damaged — ask for a fresh one" instead of a broken puzzle.

We don't need cryptographic integrity (nobody's attacking a puzzle code). We just need "did a character get mangled during paste." A simple XOR-based checksum does that for essentially zero cost.

What this means for the player

Zero of this is visible from the outside. The player taps SHARE, pastes a code to a friend, and the friend taps it to play. The 20-character string is the entire user experience.

But every one of those design decisions — Crockford Base32, variable-length packing, the CT- prefix, the checksum, the 5-char dash grouping — exists because someone, somewhere, is going to copy that code wrong, or auto-correct it, or dictate it over FaceTime, or screenshot it and OCR it. The point of the format is to not break in any of those cases.

Boring engineering. Visible as the absence of problems.
